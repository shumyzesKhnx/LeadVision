# Lead Vision

Lead Vision will help an agency research and qualify imported companies, explain their scores and review outreach drafts. **Modules 01 and 02 are implemented:** the backend foundation, persistent agency profile and service catalog. ICPs, leads, analysis and the browser interface follow in later modules.

## Run it now

The virtual environment and phase 1 dependencies are already installed in this workspace. In your IDE's PowerShell terminal:

```powershell
cd E:\LeadVision
.\scripts\start.ps1
```

Keep that terminal running, then open:

- [Swagger](http://127.0.0.1:8000/docs): expand `GET /api/v1/health`, select **Try it out**, then **Execute**.
- [Health response](http://127.0.0.1:8000/api/v1/health): check the JSON directly.

Stop the server with **Ctrl+C**. The script uses the existing project virtual environment. If PowerShell blocks script execution, use the direct commands below. If port 8000 is in use, copy `backend/.env.example` to `backend/.env`, set `LEADVISION_API_PORT=8001`, restart and use port 8001 in your browser.

Direct startup without a PowerShell script:

```powershell
cd E:\LeadVision\backend
..\.venv\Scripts\python.exe -m app
```

Expected health fields:

```json
{
  "status": "ok",
  "schema_version": 2,
  "database": {"status": "ready"},
  "worker": {"status": "not_implemented"},
  "ollama": {"status": "unavailable"}
}
```

The real response also includes version, time and explanatory messages. Ollama may say `available` if it is running locally. An unavailable Ollama does not prevent agency/service operations. No models are downloaded or generated by modules 01–02. Follow the [agency/service Swagger walkthrough](docs/phase-02-agency-and-services.md) to try the new endpoints.

Swagger's default JavaScript/CSS assets load from a CDN, so its page currently needs internet. The health endpoint, database and tests work offline after dependencies are installed. A complete saved-evidence offline interface is a later phase requirement.

## What the files do

```text
LeadVision/
  backend/
    app/                       # Python API, services and database code
    tests/                     # Backend tests
    pytest.ini
    requirements.in
    requirements.lock.txt
    .env.example
  frontend/                    # HTML/CSS/JavaScript interface in module 15
  scripts/                     # Start and test helpers
  docs/                        # Design, plans and verification
  data/                        # Local database and artifacts (ignored)
  .venv/                       # Existing Python environment (ignored)
  .cache/                      # Tool downloads (ignored)
  .gitignore
  README.md
```

| Location | Purpose |
|---|---|
| `backend/app/main.py` | Creates the API and initializes the database during startup |
| `backend/app/__main__.py` | Starts the server with the configured loopback address/port |
| `backend/app/core/` | Configuration, UTC time, hashes, errors, request guards and safe file storage |
| `backend/app/db/` | Connections, short transactions and numbered migrations |
| `backend/app/models/` | Foundation database tables |
| `backend/app/schemas/` | Allowed response/error formats |
| `backend/app/services/` | Activity recording, maintenance flag and file-cleanup helpers |
| `backend/app/api/health.py` | The health endpoint |
| `backend/tests/` | Offline automated checks using temporary databases/files |
| `data/` | Local runtime database and artifacts; excluded from Git |

SQLite creates `data/leadvision.sqlite3` on first start. Startup applies numbered migrations once and verifies their checksums on later starts. Migration 002 adds agency/services while retaining existing records. Never edit an applied migration; add the next numbered migration when a later module changes the schema. Do not delete the database to fix an error: it contains your project records.

## Tests

In a second PowerShell terminal:

```powershell
cd E:\LeadVision
.\scripts\test.ps1
```

Tests use temporary data, not your application database. They check persistence after restart, transaction rollback, migration integrity, foreign keys, file paths/junctions, activity retry handling, maintenance, Host/Origin guards and error redaction. The worker queue and coordinated backup are not implemented yet.

To apply/verify migrations without starting the server:

```powershell
cd E:\LeadVision\backend
..\.venv\Scripts\python.exe -m app.db.migration_runner
```

## Fresh setup on another checkout

Phase 1 was tested on Windows 11 with Python 3.14.8. This does not establish compatibility with future AI/CV packages. Install Python first, then run:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.lock.txt
cd backend
..\.venv\Scripts\python.exe -m pytest
..\.venv\Scripts\python.exe -m app
```

For this workspace, use the existing environment instead. It was created with `uv` and does not require pip to run. `backend/requirements.in` lists direct dependencies; `backend/requirements.lock.txt` pins the tested complete dependency set. Initial dependency installation needs internet. All core services remain bound to local addresses.

Configuration defaults work without `.env`. To customize them:

```powershell
cd E:\LeadVision
Copy-Item backend\.env.example backend\.env
```

`LEADVISION_DATABASE_MUST_EXIST=true` refuses a missing or uninitialized database, useful for future restore verification. Actual `backend/.env`, runtime data and model weights are excluded from Git. Runtime data paths remain relative to the project root, even when starting from `backend/`. The maintenance flag only blocks new writes; it is not yet a complete safe-backup procedure.

Git was not found in the terminal during implementation. Install/configure Git and verify `git --version`, then initialize local history early. Nothing has been pushed to GitHub; repository visibility must be confirmed before the first push.

# Lead Vision

Lead Vision will help an agency research and qualify imported companies, explain their scores and review outreach drafts. **Modules 01-06, live and saved evidence in 07, local NLP in 08, image measurements in 09, semantic matching in 10, explained scoring in 11, agency knowledge/retrieval in 12, and outreach drafting/review in 13 are implemented:** foundation, agency/services, versioned customer profiles, campaigns and company leads/CSV import, persistent processing jobs, saved text/image evidence, and source-linked business analysis. Live website collection now feeds the analysis pipeline. A local browser workspace now lets you test these completed modules without Swagger; see docs/frontend-demo.md. Follow the [Phase 5 Swagger walkthrough](docs/phase-05-leads-and-imports.md) to add companies manually or import a small CSV.

## Run it now

The virtual environment and phase 1 dependencies are already installed in this workspace. In your IDE's PowerShell terminal:

```powershell
cd E:\LeadVision
.\scripts\start.ps1
```

Keep that terminal running, then open:

- [Your workspace](http://127.0.0.1:8000/): use the green frontend to manage records, run research and view results. Follow the [short demonstration guide](docs/frontend-demo.md).
- [Swagger](http://127.0.0.1:8000/docs): optional API documentation.
- [Health response](http://127.0.0.1:8000/api/v1/health): check the JSON directly.

Stop the server with **Ctrl+C**. The script uses the existing project virtual environment. If PowerShell blocks script execution, use the direct commands below. If port 8000 is in use, copy `backend/.env.example` to `backend/.env`, set `LEADVISION_API_PORT=8001`, restart and use port 8001 in your browser.

Direct startup without a PowerShell script:

```powershell
cd E:\LeadVision\backend
..\.venv\Scripts\python.exe -m app
```

Expected health fields:

```json
{
  "status": "ok",
  "schema_version": 14,
  "database": {"status": "ready"},
  "worker": {"status": "available"},
  "ollama": {"status": "unavailable"}
}
```

Start the separate worker in a second terminal with `.\scripts\worker.ps1`. Without it, worker status is `unavailable`; agency, profile, campaign and lead operations still work. The real response also includes version, time and explanatory messages. Ollama may say `available` if it is running locally. An unavailable Ollama does not prevent agency/service operations. No models are downloaded or generated by modules 01–02. Follow the [agency/service Swagger walkthrough](docs/phase-02-agency-and-services.md) to try the new endpoints.

Swagger's default JavaScript/CSS assets load from a CDN, so its page currently needs internet. The health endpoint, database and tests work offline after dependencies are installed. The new frontend uses local assets and opens offline; saved-evidence research uses your installed local models.

## What the files do

See [the module folder guide](docs/project-structure.md) for the complete hierarchy.

```text
LeadVision/
  backend/
    app/                       # Python API, services and database code
    tests/                     # Backend tests
    pytest.ini
    requirements.in
    requirements.lock.txt
    .env.example
  frontend/                    # Local HTML/CSS/JavaScript workspace
  scripts/                     # Start and test helpers
  docs/                        # Design, plans and verification
  data/                        # Local database and artifacts (ignored)
  .venv/                       # Existing Python environment (ignored)
  .cache/                      # Tool downloads (ignored)
  .gitignore
  README.md
```

| Location | Purpose |
|---|---|
| `backend/app/main.py` | Creates the API and initializes the database during startup |
| `backend/app/__main__.py` | Starts the server with the configured loopback address/port |
| `backend/app/modules/` | Each feature keeps clearly named API, schema, service, model and query files in one folder |
| `backend/app/modules/foundation/` | Shared configuration, safety, database, migrations and health |
| `backend/app/modules/processing/` | Separate worker, stage handlers, queue and recovery |
| `frontend/modules/` | Separate frontend screens and result cards by feature |
| `frontend/shared/` | API requests, shared UI controls, workspace state and theme |
| `scripts/worker.ps1` | Starts the single processing worker |
| `backend/tests/` | Offline automated checks using temporary databases/files |
| `data/` | Local runtime database and artifacts; excluded from Git |

SQLite creates `data/leadvision.sqlite3` on first start. Startup applies numbered migrations once and verifies their checksums on later starts. Migration 002 adds agency/services while retaining existing records. Never edit an applied migration; add the next numbered migration when a later module changes the schema. Do not delete the database to fix an error: it contains your project records.

Migration 003 adds customer profiles and immutable configurations without rewriting agency/services. Renaming a profile changes its edit revision; changing analytical settings also appends a configuration version. Explained scoring and affected-score counts are implemented in module 11.

Migration 004 adds campaigns with workspace/ICP ownership constraints and an activity foreign key, retaining prior history and file-cleanup links. Campaign archive and ICP archive block new leads/imports; job preflight integration is implemented in module 06. Migration 005 adds shared domain identities, campaign-specific leads, append-only entered facts and lead activity foreign keys. CSV uploads use pinned python-multipart, a streamed request/file size limit and independently committed row reports. No websites are fetched by these modules.

## Tests

In a second PowerShell terminal:

```powershell
cd E:\LeadVision
.\scripts\test.ps1
```

Tests use temporary data, not your application database. They check persistence after restart, transaction rollback, migration integrity, foreign keys, file paths/junctions, activity retry handling, maintenance, Host/Origin guards and error redaction. Worker tests also check duplicate requests, cancellation, short transactions, singleton locking, bounded cooperative processing and recovery after a worker process stops. Coordinated backup follows in module 19.

The test script gives each run its own temporary data and pytest cache under `.cache/test-runs/`, avoiding conflicts with old Windows temporary folders or shared caches. These files are excluded from Git. If PowerShell blocks the script, use `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test.ps1`; this applies only to that PowerShell process.

To apply/verify migrations without starting the server:

```powershell
cd E:\LeadVision\backend
..\.venv\Scripts\python.exe -m app.modules.foundation.migration_runner
```

## Fresh setup on another checkout

Phase 1 was tested on Windows 11 with Python 3.14.8. This does not establish compatibility with future AI/CV packages. Install Python first, then run:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.lock.txt
cd backend
..\.venv\Scripts\python.exe -m pytest
..\.venv\Scripts\python.exe -m app
```

For this workspace, use the existing environment instead. It was created with `uv` and does not require pip to run. `backend/requirements.in` lists direct dependencies; `backend/requirements.lock.txt` pins the tested complete dependency set. Initial dependency installation needs internet. All core services remain bound to local addresses.

Configuration defaults work without `.env`. To customize them:

```powershell
cd E:\LeadVision
Copy-Item backend\.env.example backend\.env
```

`LEADVISION_DATABASE_MUST_EXIST=true` refuses a missing or uninitialized database, useful for future restore verification. Actual `backend/.env`, runtime data and model weights are excluded from Git. Runtime data paths remain relative to the project root, even when starting from `backend/`. The maintenance flag only blocks new writes; it is not yet a complete safe-backup procedure.

Git was unavailable during the initial setup; this workspace now has local Git history. Use `git status` to review changes and commit tested phases. The `/models/` ignore rule excludes root-level downloaded weights while allowing backend model source files into Git. Keep the GitHub repository private unless you explicitly choose otherwise. Database/settings files remain excluded.

Migration 006 adds jobs, stage records and immutable analysis runs. A run saves the lead and ICP inputs it used; later edits mark its response stale without rewriting history. Job initiation and retry require an Idempotency-Key. One lead can have only one queued/running analysis. Cancellation preserves committed stage outputs, and deletion waits until its job is terminal.

Migration 007 adds durable saved-upload manifests and evidence provenance/reviews. Upload UTF-8 text and/or static PNG/JPEG, then submit a job with its token. Original files remain unchanged. Owned artifact routes verify hashes; review changes affect input currentness. Expired unattached uploads and deleted-lead files use durable cleanup tasks processed by the worker. See [Phase 7](docs/phase-07-saved-evidence.md).

Migration 008 adds immutable business analyses, runtime-model readiness and bounded private diagnostics. The worker uses installed qwen2.5:3b by default, without automatic downloads. Generated fields remain separate from entered lead facts and always need review. Invalid employee counts become unknown; manual corrections take precedence. Exact-input caches include model digest, prompt/schema, parameters, selected evidence, reviews and manual input revisions. API editing works with Ollama unavailable.

## Agency knowledge and retrieval

Open **Agency knowledge** in the browser workspace. Add your agency facts or upload a UTF-8 TXT file, review and approve the version, then choose **Index current version**. The worker creates bounded passages and local MiniLM embeddings. **Try retrieval** shows up to three relevant source passages; fictional demo material is excluded unless explicitly enabled. Editing facts requires new approval and indexing. This prepares grounded sources for Phase 13 outreach; it does not generate or send messages. The existing theme and flat module structure remain unchanged.
